# 8Bars 产品定义与 MVP 路线图

更新时间：2026-11-10

## 1. 产品判断

8Bars 的产品机会在于让普通音乐爱好者更容易和朋友一起创作，而不是与专业 DAW 争夺完整的制作能力。用户不需要学习复杂工程，也不需要约定同时在线；每个人录制一段，作品逐步成形。

当前项目已有多个产品和技术部件，但尚未通过真实用户、跨设备的端到端测试。因此项目状态定义为：**功能原型，MVP 验证尚未完成**。

## 2. 产品定义

**产品定位**：面向有基础演奏或歌唱能力、想和朋友轻松玩音乐的爱好者，提供基于链接邀请、分段录音和异步合奏的轻量协作空间。

**核心承诺**：创建一个音乐房间，邀请朋友各自贡献一段，最后听到属于你们的合奏。

**不做什么**：8Bars 不是专业多轨 DAW，不要求用户学习音乐理论，也不以 AI 独立生成一首完整歌曲作为主要价值。

## 3. 目标用户与核心假设

### 首批用户

- 会一点乐器或演唱，但不熟悉专业制作软件的音乐爱好者。
- 有可以邀请的朋友或熟人，愿意通过轻松的共同创作获得社交乐趣。
- 首轮验证以邀请关系为入口，不依赖陌生人社区的冷启动。

### 待验证假设

1. 用户愿意创建房间并把链接发给具体的人。
2. 被邀请者能理解如何选择声部并完成录制。
3. 保存后的录音能稳定地进入合奏，协作者能听见同一版本。
4. 完成一次后，参与者愿意继续补充声部、换 Take 或再创建一间房。

这些是产品假设，不是已验证结论。

## 4. MVP 核心闭环

1. 发起人创建房间，获得可分享链接。
2. 朋友从链接进入房间，无需经过复杂注册流程。
3. 参与者选择一个可录制的声部，完成录音并试听。
4. 参与者保存 Take；当前播放版本被明确标识并同步给房间其他人。
5. 双方播放合奏，能够判断下一步是重录、选择其他 Take，还是邀请更多朋友。

**双人即可完成 MVP 验收，不要求四席全满。**系统当前有鼓、贝斯、和弦、旋律等角色，但这些角色数量不是产品价值的验收指标。

## 5. 音乐起点原则

- 模板或伴奏提供可开始创作的节奏、和弦和速度，不应伪装成固定的 AI 完整作品。
- 主旋律默认留给用户，不自动放入一条必须接受的 AI 主旋律。
- 当前程序化编曲仍需按音乐听感逐项验证；音色技术上能播放不等于模板听起来合适。
- 模板列表来自 Supabase 数据，产品设计不应把 8Bars 永久锁定在当前模板数量。用户自定义模板可在 MVP 验证后再决定。

## 6. MVP 范围

### 必须可用

- 房间创建与可访问的分享链接
- 邀请者从另一设备或浏览器进入同一房间
- 麦克风权限与录音状态反馈
- 共享 Take 采用耳机录制引导；当前不提供扬声器外放时直接提交正式 Take 的路径
- 录制、试听、重录、保存一个 8 小节 Take
- Take 持久化；刷新或另一人加入后仍可读取
- 选择当前播放版本，并将该选择同步到协作者
- 各声部按同一房间节奏播放，能听到参与者录音和伴奏
- 上传失败、权限拒绝和音频不支持时给出明确提示

### 暂缓

- 大规模公开广场、推荐排序和排行榜
- 点赞等低优先级互动
- 大量模板与用户自定义编曲器
- 复杂个人主页、虚拟角色成长和付费模式
- 让四个席位必须全部有人才能得到完整体验
- 专业级剪辑、效果器与完整混音工程

## 7. 验收标准

第一轮验收使用两个独立浏览器或设备，并由两个真实参与者完成：

- 发起人可创建房间并分享链接。
- 邀请者可打开链接并加入，不需要开发者手动修复数据。
- 邀请者能完成录音、试听和保存；发起人能看到该 Take。
- 双方刷新后仍能读取已保存音频和当前播放版本。
- 双方播放时听到同一套节奏位置和选定版本；不同声部没有明显错位。
- 用户无需口头指导就知道如何开始、保存和试听。
- 至少一位参与者主动表达继续创作、重录或邀请下一位的意愿。

耳机要求的验证重点：记录用户因暂时没有耳机而退出或延后的情况。若因此明显阻断参与，再设计不会把伴奏录进麦克风的“无耳机草稿”方案；不以未经验证的回声消除作为音质保证。

第一轮采用观察和访谈记录，不预设行业转化率门槛；收集完成率、卡点和复用意愿后再决定量化目标。

## 8. 当前实现状态

| 能力 | 当前完成度 | 代码依据 | 缺失项与验收重点 |
|---|---|---|---|
| 房间创建和分享 | 代码已实现，未做跨会话验收 | `HomeApp.tsx`、`lib/api/rooms.ts`、`BandShareCardModal.tsx` | 用新匿名会话打开链接，确认房间可读且创建过程稳定 |
| 匿名加入 | 代码已实现，依赖远端策略 | `lib/supabase/auth.ts`、`RoomView.tsx`、初始迁移 RLS 策略 | 确认另一设备能读取房间、认领/录制声部，且无需手工修库 |
| 麦克风录音 | 代码已实现，错误反馈已补，未做设备验收 | `StudioRecordingModal.tsx` | 验证允许/拒绝权限、设备缺失、浏览器录音格式和完整 8 小节流程 |
| Take 上传和持久化 | 代码已实现，未做远端验收 | `lib/api/rooms.ts` 的 `saveTake()` | 验证 Storage 上传、数据库写入、失败重试及另一会话读取 |
| 多 Take 与当前版本 | 代码和迁移已实现，远端迁移状态未知 | `saveTake()`、`activateTakeIfEmpty()`、`setActiveTake()`、多 Take 迁移 | 确认迁移已部署；验证并发保存、切换、刷新后两端版本一致 |
| Realtime 同步 | 代码和发布配置已实现，未做双端验收 | `RoomView.tsx` 的 Postgres Changes 订阅、多 Take 迁移 | 验证不同匿名会话实时收到 Take 与活跃版本更新，并覆盖断线重连 |
| 伴奏播放 | 代码已实现，音乐质量和设备兼容性未验证 | `services/audioEngine.ts`、`data/templateArrangements.ts` | 听测各模板；验证安全上下文、不同浏览器及真人录音混合播放 |
| WAV 导出 | 代码已实现，未做完整回归 | `lib/exportWav.ts`、`RoomView.tsx` | 验证真人录音、伴奏、当前 Take 和导出文件在实际浏览器中的结果 |
| 双人共同创作闭环 | **未验收** | 上述模块已具备主要代码路径 | 缺少两名真实参与者、两个独立会话从分享链接到共同试听的完整证据 |

完成度口径：**代码已实现**表示仓库中存在相应实现，不代表远端配置正确或用户流程通过；**未验收**必须由独立浏览器/设备的真实流程验证。当前已运行 TypeScript 检查，但它不能替代麦克风、Storage、Realtime、混音与试听验收。

## 9. 实施计划

| 阶段 | 状态 | 工作与完成标准 |
|---|---|---|
| 1. 产品基准 | 已完成 | README 与本文件统一产品定位，并区分代码能力和用户验证 |
| 2. 现状审计 | 已完成 | 架构、技术文档已按当前房间、Take、音频与实时同步实现校准 |
| 3. 核心可靠性 | 进行中 | 已修复录音保存失败误报成功和麦克风授权失败仍进入录制的问题；需完成双会话端到端验收 |
| 4. 体验收敛 | 部分完成 | 已补录音保存状态、错误反馈和麦克风错误提示；首次使用是否无需讲解仍需观察 |
| 5. 小规模验证 | 未开始 | 邀请目标用户试用并记录完成率、卡点和继续创作意愿 |

每个阶段完成后更新状态，不把规划中的功能写成已完成能力。

## 10. 接下来优先做什么

1. 确认 Supabase 远端已应用多 Take 迁移，并检查 Storage、RLS 与 Realtime 配置。
2. 用两个独立浏览器/设备完成创建、分享、加入、录音、保存、另一端试听和刷新恢复。
3. 记录每个失败点与浏览器/设备信息，修复后重复整条验收流程。
4. 完成至少一轮目标用户观察，再决定 MVP 是否通过以及社区功能的优先级。
